# KILN-11: Approval states and history

- Release: v0.2 · Status: doing · Owner: Claude (deliver-loop)

## Story

As a **lead reviewing an artist's work**, I want to approve a version or send it back for changes, with a short note, so that the artist and the rest of the studio know where each asset stands without asking.

As an **artist or producer**, I want to see each asset's review state on its card and in its inspector, filter the gallery by it, and read who decided what and when, so that I know what to fix next and what is done.

INVEST: Independent ☑ (needs KILN-12's users, KILN-10's version-level review and KILN-35's inspector) · Negotiable ☑ (one decision per version before chains or required reviewers) · Valuable ☑ (the v0.2 goal names `in_review → approved / changes_requested`) · Estimable ☑ · Small ☐ → built in commits that each pass the gates (api + db, web feature, e2e) · Testable ☑

## Non-functional

- Security: OWASP ASVS 5.0 V8 (one policy; scopes per action), API1/API5, CSRF and tokens per ADR 0013; notes rendered as text, never HTML; no notes in logs; every integer decoded from a cursor bounded before it reaches the database.
- Concurrency: compare-and-set on `(review_state, review_revision)` and, for a decision, `status = 'ready'`, in the `UPDATE` itself; no lock held across the request; tested with a deterministic interleaving and twelve callers on their own connections.
- Performance: a history page is one query (keyset on `uq_review_events_version_id_sequence`, actor by `pk_users`); asset states for a gallery page are one `DISTINCT ON (asset_id)` query over `uq_asset_versions_asset_id_number`; the transition is two statements plus the event insert.
- Data: migration 0011 is safe on a live `asset_versions` (plan below); history is append-only (trigger).
- Accessibility: WCAG 2.2 AA; colour never the only signal (1.4.1); outcomes in a polite status region (4.1.3); targets ≥ 24 px (2.5.8).

## Out of scope (follow-ups)

Multi-step approval chains; required reviewers or a quorum; forbidding self-approval; notifications and mentions; approvals on individual comments; server-side filtering and sorting of the gallery by state (the toolbar filters the loaded pages, as KILN-35 does for kind); a history across all versions of an asset; realtime updates (refetch on focus).

## Design

- **State machine** (`domain/reviews.py`, ADR 0015):

  | From \ action       | approve    | request_changes     | reopen      |
  | ------------------- | ---------- | ------------------- | ----------- |
  | `in_review`         | `approved` | `changes_requested` | refused     |
  | `approved`          | refused    | refused             | `in_review` |
  | `changes_requested` | refused    | refused             | `in_review` |

  Order of checks: stale `expected_state` → 409 `REVIEW_STATE_CONFLICT`; not in the table → 409 `INVALID_REVIEW_TRANSITION`; approve or request changes on a version that is not `ready` → 409 `VERSION_NOT_READY`; the note → 422 `INVALID_REVIEW_NOTE`. Both conflict problems carry `current_state` (RFC 9457 extension member).

- **API** (tag `reviews`; both security schemes; 401/403/404/409/413/422/503 problem details): `POST /api/v1/asset-versions/{version_id}/review-transitions` (`{action, expected_state, note?}`, optional `Idempotency-Key`; `201` + `Location: /api/v1/review-events/{id}`), `GET /api/v1/asset-versions/{version_id}/review-history` (`limit` 1–100, default 50; number cursor bounded to 2^31 − 1), `GET /api/v1/review-events/{event_id}`. `ReviewEventOut {id, version_id, sequence, action, from_state, to_state, actor {id, display_name}, note, created_at}`. `AssetOut.review_state` (newest version's), `VersionOut.review_state`, `VersionOut.review_revision`.
- **Layers**: `routes/reviews.py` → `services/reviews.py` (`ReviewService`, one unit of work per use case: idempotency claim, version and asset loaded, `authorize`, `decide`, `tx.reviews.record`, key completed) → `domain/reviews.py` (`REVIEW_TRANSITIONS`, `decide`, `clean_review_note`) and `domain/authorization.py` (`READ_REVIEWS` → read, `REVIEW_VERSIONS` → write) → `repositories/reviews.py` (`SqlReviewStore.record` compare-and-set, `history_page`, `event_view`). `SqlAssetRepository.newest_review_states(asset_ids)` gives the gallery and the detail their asset state.
- **Data** (migration 0011): `asset_versions.review_state text NOT NULL DEFAULT 'in_review'` and `review_revision integer NOT NULL DEFAULT 0`; checks `ck_asset_versions_review_state`, `ck_asset_versions_review_revision_non_negative`. `review_events (id, version_id → asset_versions ON DELETE CASCADE, sequence, action, from_state, to_state, actor_id → users, note, created_at)`, unique `(version_id, sequence)`, checks on each enum, the transition table (`ck_review_events_transition`) and the note length; trigger `review_events_append_only` refuses updates and direct deletes (a cascade from a deleted version runs at trigger depth 2 and passes).
- **Backfill and lock plan**: no batches are needed. On PostgreSQL ≥ 11 `ADD COLUMN … NOT NULL DEFAULT <constant>` stores the default in the catalogue, so existing rows read `in_review` / 0 without a rewrite (set-based, zero row writes; `test_migration_0011_puts_existing_versions_in_review_without_rewriting_the_table` checks the table keeps its file). Each `ADD COLUMN` takes a brief ACCESS EXCLUSIVE lock bounded by env.py's 5 s `lock_timeout` (tested behind a writer). Checks and the new table's foreign keys are added `NOT VALID` and validated after the DDL commits (SHARE UPDATE EXCLUSIVE: reads and writes go on). The new table is empty, so its unique index is built plainly, not `CONCURRENTLY`. Had a non-constant default been needed, the plan would have been: add the column nullable, backfill in keyset batches of 1,000 ids per transaction, then add `CHECK (… IS NOT NULL) NOT VALID`, validate, and set `NOT NULL`.
- **Web**: see the web commit; the plan is a state badge (`Badge` with tone, icon and word) on cards, in the inspector header and on each version of the timeline; a Review tab with a version picker (newest by default), the actions with an optional note (`TextArea`), a conflict message, and the history as a timeline with four states; the gallery toolbar gains a review filter and a "Needs attention" sort kept in the URL.

## Decisions for the reviewer

- The state lives on the version and the asset shows its newest version's (ADR 0015); a new version puts the asset back in review while the older version keeps its decision.
- A strict machine: a decision is changed only by reopening first, so every change of mind is recorded as two events.
- Compare-and-set on the state and the revision, not a row lock held across the request; the `ready` rule is re-checked in the same `UPDATE`.
- Any writer may review, their own uploads included (ADR 0015); self-approval rules belong with required reviewers (out of scope).
- The note is optional for every action, unlike GitHub's required body for "request changes": the detail lives in the version's comments.
- `DomainError.extensions` adds RFC 9457 extension members; only the two review conflicts use it (`current_state`).
