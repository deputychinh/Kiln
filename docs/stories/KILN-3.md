# KILN-3: Upload through presigned POST and confirm the upload

- Release: v0.1 · Status: doing · Owner: Claude (deliver-loop)

## Story

As a **studio artist**, I want to send a file straight to storage and have Kiln confirm it arrived intact, so that large textures and meshes upload quickly and nobody reviews a half-uploaded file.

INVEST: Independent ☑ (builds on KILN-2 only) · Negotiable ☑ · Valuable ☑ · Estimable ☑ · Small ☑ (API + storage adapter, no UI) · Testable ☑

## Acceptance criteria

| -------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AC1            | a valid name, file name, content type and size                                               | `POST /api/v1/assets`                                                   | `201` with `Location: /api/v1/assets/{id}`, the asset, version 1 (`pending_upload`) and an `upload` object: `url`, form `fields`, `expires_at` 15 minutes ahead |

## Non-functional

- Security (A01, A05, A06, A10): object keys come only from the server; the POST policy limits key, type and size; URLs expire after 15 minutes; completion re-checks size and type with `HEAD` (defence in depth if a storage server ignores a policy condition); request bodies limited to 1 MB by a middleware (declared or chunked, `413`), field lengths capped as well.
- Reliability: storage calls are bounded (3 s connect, 10 s read, 2 attempts in total) and surface `STORAGE_UNAVAILABLE` (`503`) instead of hanging; completion is idempotent.
- API (Zalando, RFC 9457): plural kebab-case resources, `201 + Location`, actions as sub-resources (`/completions`), `snake_case` JSON, problem details for every error, OpenAPI regenerated and web types updated.
- Performance: the API never proxies file bytes.

## Out of scope

- `Idempotency-Key` replay for `POST /assets` (filed as KILN-21), jobs and thumbnails (KILN-4), browser upload UI and bucket CORS (KILN-6), auth (KILN-12), multipart uploads above 500 MB.

## Design

- **Port** `ObjectStorage` (`ports.py`): `ensure_bucket()`, `presign_upload(key, content_type, size_bytes, ttl_seconds) -> SignedPost`, `promote(source_key, target_key, etag)`, `delete(key)`, `head(key) -> StoredObject | None`, `ping()`. Adapter `adapters.py` (`S3ObjectStorage`, boto3, SigV4, path-style; 3 s connect, 10 s read, 2 attempts; a separate 1 s single-attempt client for readiness). Fake in `tests/fakes.py`. The database engine is built in `container.py` with `lock_timeout = 5s` and `statement_timeout = 15s` so the `FOR UPDATE` path cannot hang (KILN-2 review).
- **Service** `services/assets.py` (`AssetService`): `create`, `add_version`, `complete_upload`, `get`, `list` — the only place that combines repository, storage and clock.
- **Routes** `routes/assets.py`, schemas in `schemas/assets.py` (pydantic, boundary only); composition in `container.py` with FastAPI dependencies so tests swap fakes.
- **New error codes**: `UPLOAD_NOT_FOUND`, `UPLOAD_MISMATCH` (409), `STORAGE_UNAVAILABLE` (503).
- **Tests**: service unit tests with fakes; API tests through `TestClient` with fakes; one integration test against SeaweedFS (real POST upload, then completion, then an oversized POST to record whether the policy is enforced).

### Spike result (2026-11-04)

Probed SeaweedFS 4.48 with a boto3 presigned POST: exact size → `204`; one byte more → `400 EntityTooLarge`; one byte less → `400 EntityTooSmall`; another content type → `403 AccessDenied`; another key → `403`. Only the conforming object was stored. The policy is enforced, so the completion `HEAD` check stays as defence in depth (other S3 servers may differ), not as the primary control.

### Design as built

- `adapters.py` (`S3ObjectStorage`, boto3), `services/assets.py` (`AssetService`), `schemas/assets.py`, `routes/assets.py`, `container.py` (engine with `lock_timeout` 5 s and `statement_timeout` 15 s, `pool_pre_ping`; S3 client with 3 s connect and 10 s read timeouts and 2 attempts in total), app lifespan creates the bucket and only warns if storage is down.
- The port signs with a TTL (`SignedPost`); the service owns `expires_at` through the `Clock`.
- `GET /api/v1/asset-versions/{id}` was added so the `Location` of a new version resolves.
- CORS allows `GET`/`POST` only and exposes `Location` and `X-Request-Id`.
- SeaweedFS reserves volumes per bucket, so integration tests share one `kiln-test` bucket and compose sizes volumes at 64 MB with `-volume.max=0`; the storage service has a `/healthz` healthcheck.

### Review round 1 changes (7.0/10)

- **Staging + conditional promotion** (ADR 0005): forms write `uploads/<asset_id>/<version_id>`; completion copies to the final key with `CopySourceIfMatch`, deletes staging, and resumes after partial failure.
- **Every error is problem details**: SQLAlchemy errors → `503 DATABASE_UNAVAILABLE`, lock/statement timeouts (SQLSTATE 55P03/57014) → `503 DATABASE_BUSY` with `Retry-After`, anything unexpected → `500 INTERNAL` (logged, no internals); `405 METHOD_NOT_ALLOWED`, `413 PAYLOAD_TOO_LARGE` have their own codes.
- **Time budgets** that tests pin: DB `lock_timeout` 5 s / `statement_timeout` 15 s (settings-driven), S3 3 s connect, 10 s read, `total_max_attempts` 2 (worst case 26 s).
- **OpenAPI** documents `application/problem+json` for 400/404/409/413/422/503 per route.
- **Input**: `size_bytes` is `StrictInt`; `limit` outside 1–100 is `422`; bodies over 1 MB (declared or chunked) are `413`.

Mutation checks (code restored each time). Round 1, all killed: no size/type comparison on completion; no `content-length-range` in the policy; `ExpiresIn` of 7 days; no database `connect_args` timeouts. Exploratory: form reuse after completion against the real server, swap between check and copy, interrupted completion, held row lock, chunked oversized body, boolean size, out-of-range limit, malformed ids on every route.

Round 2 (reviewer): 15 of 17 mutants killed; the two survivors — dropping `CopySourceIfMatch` from the promotion, and skipping the size/type re-check on the resume path — are now killed by `unit/test_s3_adapter.py::test_promotion_copies_only_if_the_source_etag_still_matches`, `integration/…::test_promotion_with_a_stale_etag_is_refused_by_the_real_server` and `edges::test_a_resumed_completion_still_checks_the_final_file`.

Round 2 also moved the 1 MB body limit inside CORS and the request-id middleware and handles unexpected errors there, so `413` and `500` problems keep `Access-Control-Allow-Origin` and `X-Request-Id` and the log line names the request (`edges::test_a_413_keeps_cors_and_the_request_id`, `::test_a_500_keeps_cors_and_the_request_id_and_logs_it`).

Final-round review by a fresh reviewer (8.5/10) found that two concurrent completions against **real** storage could return `503` to the loser (14.5 % of calls): its copy hit a staging object the winner had already deleted. `promote` now returns `PROMOTED`, `CHANGED` (412) or `SOURCE_GONE` (404), and `SOURCE_GONE` continues with the final-file check, so every caller gets `200 processing`. Also fixed in that round: server-side domain errors are logged with the request id and the storage error code; `405` carries `Allow`; OpenAPI documents errors only as `application/problem+json` with a published `Problem` schema, `Retry-After` on 503 and `Location` on 201; `/ready` uses a 1 s single-attempt `HeadBucket` instead of `ensure_bucket`; integration tests empty `kiln-test` after themselves; a real `statement_timeout` maps to `DATABASE_BUSY`.

Re-score of the final round (8.5/10) caught a regression introduced by the new 5xx logging: it read `cause.response.get(...)`, but botocore timeouts set `response=None`, so a hung storage returned `500` instead of `503`. The adapter now attaches a `cause_code` (S3 error code or botocore class) to `StorageUnavailableError` and the handler only logs that attribute. New tests: a real `ReadTimeoutError` through the adapter, the handler logging the cause without leaking it, a blackhole endpoint making `/ready` answer `503` with `Retry-After` in under 5 s (start-up and readiness both use the 1 s single-attempt probe client), the probe client's configuration, `/ready` never creating the bucket, and a gone source during promotion still checking the final file (`409 UPLOAD_NOT_FOUND` / `UPLOAD_MISMATCH`). Mutants N1, N2, N8 from the review are killed.

Deferred to KILN-4 (worker), recorded there: a narrow race where a second, concurrent completion could copy bytes re-posted to staging after the first one finished (the worker will verify the ETag recorded at completion before processing), and purging orphaned staging objects under `uploads/`.

Defects found in QA and fixed: a bucket per integration test exhausted SeaweedFS volumes; chunked oversized bodies came back as `400` until the middleware buffered and counted them.

Gates: `make ci` green — Python 242 passed, coverage 99 %; ruff and mypy strict clean; web e2e on the production build.
