# KILN-48 + KILN-49: Focus after a decision; every idempotency fingerprint field pinned

- Release: v0.2 · Status: doing · Owner: Claude (deliver-loop) · Debt from the KILN-11 review (one story for both items)

## Story

As a **lead who reviews with the keyboard or a screen reader**, I want focus to land somewhere sensible after I approve, request changes, reopen or delete a comment, so that I can carry on without starting again from the top of the page (KILN-48).

As a **maintainer**, I want every field that makes a request different to be pinned by a test of its idempotency fingerprint, so that a later change cannot let a retry with another body replay the first answer (KILN-49).

INVEST: Independent ☑ (KILN-11 and KILN-10 are done) · Negotiable ☑ (the focus target is a choice, recorded below) · Valuable ☑ (WCAG 2.4.3 failure; mutants that survived review) · Estimable ☑ · Small ☑ (no API or schema change) · Testable ☑

## Non-functional

- Accessibility: WCAG 2.2 SC 2.4.3 Focus Order (focus never drops to `<body>`), 2.4.7 Focus Visible (the hint and the refusal get the same ring as other controls), 4.1.3 Status Messages (each outcome reaches a screen reader through one channel: the polite region, or the focused message — never both).
- Security: the idempotency fingerprint is what stops a retry with another body from replaying the first answer (ADR 0006, ADR 0016); this item only adds tests, no behaviour change on the API.
- Performance: no extra request; the focus move waits for the refetch the decision already makes.

## Out of scope

The CLI's `expected_revision` (KILN-50); comment replay semantics (KILN-47).

## Design

- **Focus target after a decision (KILN-48).** Chosen: the first action the new state offers (Reopen after approve or request changes; Approve after reopen), falling back to the hint that says why when there is none (review round 1; it was the state line). Why: the APG dialog rule above says that when the element that had focus no longer exists, focus goes to "another element that provides logical work flow"; Approve → Reopen behaves like one toggle control whose state changed, and the APG button pattern keeps focus on a toggle (the comments' Resolve ↔ Reopen is one button and keeps focus for that reason). Focusing the state line instead would make a screen reader read "Version 2 is Approved" right after the polite status said "Version 2 approved": a double announcement. Focusing Reopen reads only "Reopen, button", so the status region is kept as it was (one queued message per outcome). The fallback is the hint ("This version can be approved or sent back once it has finished processing."; APG: a static element with `tabindex="-1"` may take focus when no control fits): it adds the reason, not the state the status has just said, so nothing is read twice, and it gets a focus ring.
- **When focus moves.** `ReviewDecision` stores the revision its decision created (`event.sequence`) and an effect moves focus once the version shown has reached it; the refetch is part of the mutation (`onSettled`), so this is one render after success. `movedForRef` makes it once per decision, so a later refetch (someone else decides) never steals focus. Buttons ignore a repeated Enter keydown (`event.repeat`), so a held key cannot approve and then reopen.
- **Refusals.** The message takes focus from an effect once it has rendered (a `requestAnimationFrame` could run before the commit: the mobile conflict journey failed 1 run in 9 that way) and has no `role="alert"`: NVDA and JAWS read a focused alert twice, and focus already reaches every user, pointer users included, because it moves on every refusal. `:focus { outline: none }` became the standard `:focus-visible` ring (review round 1). On the comments side, the only focused messages are field errors (`TextArea` describes its error through `aria-describedby`, no live role); a failed reply or edit used to leave focus on the submit button with the error unannounced, so the field now takes focus, as the composer already did. Review round 2: focusing in the same `onError` handler ran before React committed the error, so at `focusin` the field was not yet `aria-invalid` and described nothing; `useFocusAfterCommit` (an effect on a request counter, so a repeated identical error focuses again) now focuses the composer, the reply field and the edit field after the commit, for failures and for blank bodies.
- **Comment flows audited (KILN-10).** Edit → Save returns focus to Edit; Cancel/Escape to Edit or Delete; Reply → Post or Cancel to Reply; Resolve and Reopen are one button that stays (a thread hidden by Resolve sends focus to the list, KILN-10); posting keeps the Post button; Remove region focuses Mark region. One case unmounted its own button: **Delete comment**: the confirmation and the author's buttons disappear once the comment is deleted. `CommentEntry` now calls `onDeleted`, and `ThreadItem` focuses its article (`tabindex="-1"`, named "Comment n by …", focus ring already styled), so the status's "Comment deleted" is not read twice. Review round 2: when Resolve hides the thread, focus goes to the list region (KILN-10); its `:focus { outline: none }` became the standard `:focus-visible` ring, so the target stays where it was and is visible.
- **Fingerprints (KILN-49).** No code change: tests now change one field at a time. Review: `operation = review:{version_id}`, payload `{action, expected_state, expected_revision, note}`. Thread: `start_thread:{version_id}`, `{body, region: {shape, x, y, width, height} | null}`. Reply: `reply:{thread_id}`, `{body}`. Web signatures: review `[version.id, revision, action, expected state, note]`, thread `[body, region]`, reply `body`.
- **API, data, layout:** no change (no OpenAPI diff, no migration); the focus ring uses the existing focus tokens at every size class.

## Known gaps

- Only Chromium projects run the keyboard journeys; Safari's focus behaviour on `<button>` clicks is not covered.
