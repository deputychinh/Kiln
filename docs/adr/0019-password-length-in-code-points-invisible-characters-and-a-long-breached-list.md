# ADR 0019: Password length in visible code points, invisible characters ignored, a list that meets the policy, the list loaded only where a password is set

- Status: accepted · 2026-11-08 · Supersedes ADR 0017 §1 (counted after NFKC), §2 (the single list, loaded at startup), §3 ("Unicode NFKC_Casefold"), §4 (the context words and how the rest is counted) and its Context's implied ASVS V6.2.4 compliance

## Context

The independent review of KILN-39 found four gaps in ADR 0017. (1) Length was counted after NFKC, so U+FDFA (one code point, 18 characters after NFKC), five "ﬃ" ligatures or five "㎒" squares passed a 15-character minimum, while NIST SP 800-63B-4 §3.1.1.2 counts each code point once. (2) A zero-width space or a soft hyphen inside `passwordpassword` slipped past the list, and the context rule measured what was left in its case-folded form, so `ß` (which folds to `ss`) counted twice. (3) ASVS 5.0 V6.2.4 asks for at least the top 3,000 passwords _that match the policy_; only 329 entries of the NCSC list reach 15 characters. (4) The comparison key was called NFKC_Casefold but did not drop default-ignorable code points as that mapping does. ADR 0017 is accepted, so it is not edited.

## Decision

1. **Length = visible code points after NFC**, 15 to 128 (`password_length`). NFC (canonical composition, NIST's recommended form) keeps "é" typed as one or two code points at one, and never expands a compatibility character; format characters (Cf) and Unicode's other default-ignorable code points (variation selectors, the combining grapheme joiner, Hangul fillers, tags) show nothing and do not count. That is a deliberate, stricter reading of NIST's "each Unicode code point SHALL be counted as a single character": counted, fourteen letters and a zero-width space would meet the minimum with fourteen characters anyone can see. The **hashed form keeps NFKC** (KILN-12; changing it would lock out every password with a compatibility character) and is bounded separately at 512 characters (the sign-in field's 4× slack), so 29 × U+FDFA is refused even though it is 29 code points.
2. **The comparison key is NFKC → case fold → NFKC, then default-ignorable code points removed** (`password_key`). It is close to Unicode's NFKC_Casefold, not equal to it, and is described that way. NFKC rather than NFC for the key on purpose: compatibility folding makes more variants hit the list (full-width `ｐａｓｓｗｏｒｄ`), and the key is only compared, never stored. Invisible characters are **stripped, not refused**: NIST asks verifiers to accept all Unicode, and ZWJ/ZWNJ belong in emoji and Persian or Indic passphrases; stripping them only for the comparison closes the bypass without refusing such passwords. (Names refuse them instead, because a name is shown to others.)
3. **Context words**: "kiln"; the email's local part; the email's domain labels except the last (`studio` in `ada@studio.com`, so not `com`); the display name; and each one's pieces split at non-letters and `_` (3 characters or more). They are removed until none is left, and what is left must still hold 15 of the **password's own code points** — counted on the NFC password, not on the folded key — and not be on the list. Containing a context word is still fine.
4. **Two bundled lists, both from SecLists at `231fffb`**: the NCSC top 100,000 (unchanged), and every entry of 15 or more code points from Mark Burnett's "Ten Million Passwords" (2015, breached passwords he released to the public domain), 10,908 lines in their original order, derived from `xato-net-10-million-passwords-1000000.txt` (SHA-256 `424a3e03…0caf51`) with no other change; the derived file's SHA-256 `977ebd3a…6d3c37` is pinned in `constants.py`. Together 108,563 keys, of which more than 3,000 match the policy (a test pins it), which is what ASVS 5.0 V6.2.4 asks for. Provenance, both licences and the Have I Been Pwned credit are in `resources/common-passwords.LICENSE.txt`. The Pwned Passwords API states "there is no licencing or attribution requirements" (its CC BY 4.0 covers the breach and paste APIs), so the credit is a courtesy, not a licence term.
5. **Loaded only where a password is set.** `IdentityService` receives a loader and calls it in `create_user`; the API process, which never sets a password, never loads the list (about 0.02–0.05 s and about 20 MB RSS when it does, measured on a laptop). A test checks the container in a fresh interpreter.

## Consequences

- A password of 15 non-Latin compatibility characters is accepted (15 code points) as long as its NFKC form stays within 512; one of 14 ligatures is refused, whatever it expands to.
- A future password change or reset passes the display name and the email to `check_new_password`, as `create_user` does.
- A missing list file now fails at the first `create-user`, not at API startup; the checksum tests catch it in CI.
